# 双轨研发的 AI 动态研究系统 · 设计计划

> **目标**：为「工程实现类」与「工艺研发类」两类研发工作，建立一套可复用的 AI 参与机制——把散落在人脑与聊天记录里的调参经验，变成**可搜索、可复现、可漂移检测、可沉淀**的研究系统。
>
> **核心命题**：研发的本质是在高维参数空间里**找到一个稳态点，并且保持住**。AI 的价值不在于替你决定参数，而在于让「找到」更快、让「保持」可观测、让「找到的过程」变成资产。

---

## 0. 两类研发的本质差异

先分清差异，否则会用错方法——**工程类的经验直接套到工艺上，会撞墙**。

| 维度 | 工程实现类 | 工艺研发类 |
|---|---|---|
| **参数性质** | 离散 / 结构化：架构选择、依赖版本、并发度、缓存策略、超时阈值 | 连续 / 物理：曝光时间、增益、阈值、焦距、压力、温度、速度 |
| **试错成本** | 低。`git revert` 几分钟回到原点 | 高。物料、工时、可能报废样件 |
| **可并行性** | 高。git worktree 多分支同时跑 | 低。设备通常串行，一次一件 |
| **噪声水平** | 低。确定性为主，重跑结果一致 | 高。环境、设备漂移、批次差异 |
| **反馈延迟** | 秒～分钟 | 小时～天 |
| **参数耦合** | 弱。改并发度基本不影响日志格式 | 强。改曝光必然影响对比度、影响阈值效果 |
| **实验次数预算** | 几十～几百次 | 几次～几十次（稀缺） |
| **稳态判据** | 测试全绿 + 性能达标 + 可维护 | CPK ≥ 1.33 + 连续 N 件合格 + 波动带内 |
| **主要风险** | 过度设计、技术债、指标作弊 | 参数过拟合当前批次、量产漂移 |
| **AI 的主战场** | 并行探索 + 自动验证 | DOE 设计 + 代理模型 + 漂移监控 |

> **一句话**：工程类是「**便宜的多点搜索**」，工艺类是「**昂贵的少点推理**」。前者靠并行堆算力，后者靠模型省实验。

## 1. 共同骨架：六环闭环

两类研发共享同一套闭环，只是每环的实现方式不同。

```
   ┌──────────────────────────────────────────────────┐
   │                                                  │
   ▼                                                  │
① 变量空间建模                                         │
   ↓                                                  │
② 实验设计 DOE                                        │
   ↓                                                  │
③ 执行与采集（带完整上下文）                            │
   ↓                                                  │
④ 代理模型 / 响应面                                    │
   ↓                                                  │
⑤ 搜索决策（下一个点在哪）                              │
   ↓                                                  │
⑥ 稳态判定 ──未达标──→ 回到 ①/⑤                       │
   │                                                  │
   └─达标─→ 稳态监控 ──漂移──→ 回到 ① ────────────────┘
```

**每一环的产出都必须落盘**，否则闭环断在人的记忆里。

| 环 | 产出物 | MTR-P 落点 |
|---|---|---|
| ① 变量空间 | `params.yaml`：参数名/类型/范围/耦合/可调性 | P 库（配置） |
| ② DOE | `doe-plan.csv`：本次批次要跑的点 | P 库（脚本产物） |
| ③ 采集 | 原始数据 + 元数据（版本/环境/时间/操作人） | P 库（Artifact，带 SHA-256） |
| ④ 代理模型 | 模型文件 + 拟合优度 + 适用范围 | P 库（模型）+ T 库（方法卡） |
| ⑤ 搜索 | 下一批推荐点 + 推荐理由（采集函数值） | P 库（脚本产物） |
| ⑥ 稳态 | 判据定义 + 监控记录 + 漂移告警 | M 库（判据）+ T 库（记录） |

## 2. ① 变量空间建模（两类都要做，做法不同）

### 2.1 参数清单的标准结构

```yaml
# params.yaml —— 示例，参数名为占位
meta:
  project: <项目名>
  track: engineering | process        # 双轨标记，决定后续流程
  version: 0.1.0
  updated: 2026-11-11

params:
  - name: <参数名>
    type: continuous | discrete | categorical
    unit: <单位>                       # 连续量必填
    range: [<下限>, <上限>]            # 或 values: [...] 用于离散/分类
    default: <默认值>
    adjustable: true | false           # false = 本次研究锁定
    cost: low | medium | high          # 调整该参数的成本（工艺类关键）

coupling:                              # 耦合关系，工艺类必填
  - from: <参数A>
    to: <参数B>
    relation: "A↑ 导致 B↓"             # 自然语言描述，附验证来源
    verified: true | false

objective:                             # 优化目标
  primary: <指标名>
  direction: maximize | minimize
  weight: 1.0

constraints:                           # 硬约束（不可违反）
  - expr: "<指标名> <= <阈值>"
    reason: <为什么不能违反>
```

**工艺类必须填 `coupling`**。不知道耦合就盲调，等于在流沙上盖楼。

### 2.2 怎么把耦合挖出来

1. **先做一次单变量扫描**（OFAT，只用于定性摸耦合，不用于优化）
2. 观察哪些参数一动，其他指标跟着动
3. 对每个可疑耦合，让 Agent 从原理上解释"为什么会有这个耦合"
4. **解释不了但要实证存在的，标 `verified: false` 并保留**——不要因为解释不了就删掉

> ⚠️ `coupling` 里写"我猜"是最危险的。无法验证的耦合必须标注，否则后续优化会建立在错误前提上（对应原则 4 意图债）。

### 2.3 工程类的参数空间特殊处理

工程类的"参数"很多不是数值，而是**选择**：

| 类型 | 例 | 处理 |
|---|---|---|
| 离散可枚举 | 数据库选型 | 当作 categorical，每项一个分支 |
| 连续可调 | 连接池大小 | 当成连续量，但注意有平台期 |
| 结构性 | 同步 → 异步 | **不是参数，是架构决策**，单独立 ADR |

**结构性改动不要混进参数搜索**。演化和探索是两种工作，混在一起会得到一堆四不像的方案。

## 3. ② 实验设计 DOE

### 3.1 两类研发的 DOE 策略

| | 工程实现类 | 工艺研发类 |
|---|---|---|
| 初始策略 | **并行全因子**（成本低，能全跑就全跑） | **部分因子 / Plackett-Burman**（筛主效应） |
| 中期策略 | 按指标排序，淘汰差的 | **响应面法（RSM）/ 拉丁超立方** |
| 后期策略 | 局部微调 | **贝叶斯优化**（每次实验后更新推荐） |
| 每批点数 | 5～20（并行跑） | 3～8（设备节奏） |

### 3.2 关键原则：不要一次只改一个

**OFAT（One Factor At a Time）是工艺研发最常见的错误**：它无法发现交互效应，而且实验次数是 O(n) 而非 O(log n)。

> 举例：曝光 ↑ 让对比度 ↑（好），但阈值 ↑ 让对比度 ↓（坏）。单看各自都是单调的，组合起来存在一个中间最优带——OFAT 永远找不到这个带。

### 3.3 与 AI 的协作方式

**AI 负责生成设计，人负责审核成本**：

```markdown
# DOE Agent 提令模板

给定 params.yaml 和本次预算（N 次实验），输出：
1. 推荐设计方法（部分因子 / RSM / LHS / BO）及理由
2. 具体实验点表（CSV 格式）
3. 每个点要采集哪些指标
4. 预期能从这批数据中回答什么问题
5. 这批数据回答不了什么问题 ← 必填，防止过度解读
```

第 5 条是必须的。**每次实验都要明确"这批数据不能证明什么"**，否则代理模型会被外推到它不该覆盖的区域。

## 4. ③ 执行与采集：上下文比数据重要

### 4.1 每次实验必须记录的最小集

```json
{
  "run_id": "<唯一ID>",
  "timestamp": "<ISO8601>",
  "track": "engineering | process",
  "params": { "<参数名>": "<值>" },
  "env": {
    "code_commit": "<git sha>",
    "config_hash": "<sha256>",
    "machine": "<设备/机器标识>",
    "ambient": { "<温湿度等环境量>": "<值>" }
  },
  "raw_data_ref": "artifact://<path>",
  "raw_data_sha256": "sha256:<hash>",
  "metrics": { "<指标名>": "<值>" },
  "notes": "<异常/观察>",
  "operator": "<人 or agent id>"
}
```

**没有 `code_commit` + `config_hash` 的实验记录等于废数据**——三个月后你无法复现，也无法判断两次差异是参数造成的还是版本造成的。

### 4.2 工程类的采集：让 CI 顺手做

工程类天然有 CI，直接挂上去：

```yaml
# 每次跑完自动产出一条 run record
- run: <benchmark/test>
  on_success: emit_run_record()
```

**不要人工填表**。人工填表的数据三个月后必然残缺。

### 4.3 工艺类的采集：人机分工

| 步骤 | 谁做 | 为什么 |
|---|---|---|
| 参数设置 | 人 | 设备操作规范，安全 |
| 数据采集 | 脚本/设备接口 | 避免手工转录错误 |
| 环境量记录 | 自动 | 人手记不住 |
| 异常判断 | 人 | 现场感知无法替代 |
| 结果录入 | 脚本读设备导出 | 减少中间环节 |

> **工艺类最容易丢的数据是"环境"和"异常"**。温度差 2℃、设备刚保养完、换了批次物料——这些不记，后面拟合出来的模型全是噪声。

## 5. ④ 代理模型（工艺类的核心，工程类可选）

### 5.1 为什么需要

工艺类实验次数稀缺（可能只有 20 次预算），无法直接搜索高维空间。代理模型用少量点拟合响应面，让搜索在**模型上**进行，而不是在真实设备上。

### 5.2 模型选型建议

| 数据量 | 推荐 | 理由 |
|---|---|---|
| < 15 点 | 高斯过程（GP） | 自带不确定性估计，适合贝叶斯优化 |
| 15～50 点 | GP 或 随机森林 | RF 更稳，但无不确定性 |
| > 50 点 | 梯度提升树 / 小型 MLP | 表达力够，但要额外做不确定性估计 |
| 有明确物理模型 | **混合模型**（物理 + 残差学习） | 最优。物理约束防止外推失控 |

### 5.3 必须报告的三个数

1. **拟合优度**（R² / RMSE）—— 但这不是重点
2. **留一交叉验证误差**（LOOCV）—— 更重要，反映泛化
3. **适用范围**（采样凸包的边界）—— 最重要，防止外推

> **代理模型只在采样点围成的区域内可信**。跑到外面去，它给的是幻觉——而且是带着置信区间伪装的幻觉。

### 5.4 工程类要不要做代理模型

多数情况不需要。工程类实验便宜，直接真跑就行。**例外**：性能优化这类单次实验耗时很长的场景（如压测 4 小时），值得做。

## 6. ⑤ 搜索决策：下一个点在哪

### 6.1 采集函数（Acquisition Function）

工艺类用贝叶斯优化，核心是平衡「利用」与「探索」：

| 策略 | 公式直觉 | 适用 |
|---|---|---|
| **EI**（期望改进） | 这个点比当前最优好的期望值 | 默认首选 |
| **UCB**（置信上界） | 均值 + κ×标准差 | 想更激进探索时调大 κ |
| **PI**（改进概率） | 比最优好的概率 | 接近收敛时 |

**κ 或 ξ 这些探索参数要有明确取值理由**，不能默认。

### 6.2 工程类的搜索：不需要贝叶斯

工程类直接**并行跑 + 排序淘汰**更高效：

```
批次1：8 个候选方案并行（不同 worktree）
  ↓ 跑各自验证
批次2：保留 top 3，各做 2 个变体
  ↓
批次3：1 个胜出，做边界测试
```

这就是遗传算法的简化版。**别为了"高级"上贝叶斯优化，工程类的瓶颈从来不是采样效率，是验证带宽**（对应原则 8 WIP 上限）。

### 6.3 AI 的推荐必须可质疑

每次推荐都要附：

- 推荐点的坐标 + 采集函数值
- **为什么是这个点**（利用当前最优？还是探索不确定区？）
- **如果这个点失败，说明什么**（可证伪性）

对应原则 22（持续质疑）——**推荐理由写不出来的建议不要采纳**。

## 7. ⑥ 稳态判定与保持（最容易被糊弄的一环）

### 7.1 稳态判据必须写死

**"感觉差不多了"不是稳态。** 稳态必须同时满足四个条件：

```yaml
steady_state:
  metrics:                     # 1. 指标达标
    - name: <指标>
      target: <目标值>
      tolerance: <±容差>        # 必须给容差，不给就不叫判据
  
  window:                      # 2. 观察窗口
    samples: 30                # 连续多少件/次
    duration_min: 120          # 或者连续多长时间
  
  stability:                   # 3. 稳定性（不只是均值达标）
    cpk_min: 1.33              # 工艺类
    std_max: <上限>            # 工程类可看抖动
    trend_test: "no_drift"     # 斜率不显著
  
  exit_criteria:               # 4. 退出条件（什么情况判定失稳）
    - "<指标> 连续 3 次超差"
    - "<指标> 均值偏移 > 2σ"
    - "环境量超出 <范围>"
```

**四个条件缺一个，就等于没有稳态定义。**

### 7.2 三态机 + 漂移触发

```
        ┌─────────────┐
        │  探索态      │  大范围撒点，找可行域
        │ Exploration │
        └──────┬──────┘
               │ 找到可行域
               ▼
        ┌─────────────┐
        │  收敛态      │  局部细化，逼近最优
        │ Convergence │
        └──────┬──────┘
               │ 达到稳态判据
               ▼
        ┌─────────────┐
        │  稳态态      │  锁定参数，持续监控
        │  Steady     │
        └──────┬──────┘
               │ 漂移检测触发
               ▼
        回到探索态（带历史先验，不是从零开始）
```

**关键设计：漂移后回探索态，但带着历史数据当先验。**不是推倒重来，是"我大概知道在哪，但需要重新确认"。

### 7.3 漂移检测怎么做

| 方法 | 信号 | 适用 |
|---|---|---|
| 控制图（X-bar / EWMA） | 均值缓慢漂移 | 工艺类首选 |
| 残差监控 | 实际值偏离代理模型预测 | 有代理模型时 |
| 分布检验（KS / PSI） | 数据分布变了 | 换批次/换物料 |
| 环境量关联 | 指标异常时环境量也异常 | 排查根因 |

**漂移告警必须有"分级"**：
- 🟡 轻微偏移 → 记录，不动作
- 🟠 趋势性偏移 → 触发参数微调建议
- 🔴 超差 → 立即停线，人工介入

对应原则 12（检测与可观测）——**变更不算完成，直到系统能观察它的效果**。

## 8. 与 MTR-P 体系的接口

这套研究系统不是独立的，它应该长在 MTR-P 上：

| 研究对象 | 去哪里 | 为什么 |
|---|---|---|
| 变量清单、稳态判据、有效参数区间 | **M 库**（向量知识库） | 已验证，可复用，跨项目可查 |
| 实验脚本、配置、原始数据、模型 | **P 库**（Git + Artifact） | 需要版本控制和可复现 |
| 方法卡（怎么找到的、踩了什么坑） | **T 库**（Obsidian 个人知识库） | 待验证的方法论，供人策展 |
| 失败的参数组合、走不通的方向 | **R 库**（冷宫） | **负样本史**，珍贵 |
| 跨库检索 | **知识路由中间件**（原则 19） | 新增 intent: `experiment_design` |

### 8.1 路由中间件要新增的 intent

```yaml
read:
  intents:
    experiment_design:
      plan: [P, M, T]          # 先看历史实验，再看已验证方法
      weights: { P: 1.0, M: 0.8, T: 0.6 }
      fallback: [R]            # 兜底查负样本（别忘了这个）
```

**兜底查 R 库是关键设计**——找新方案前先看"以前试过什么不行"，避免重复踩坑（对应原则 21 的取数逻辑）。

## 9. 落地路线（分四阶段，别一次做完）

### P0：手工闭环（1～2 周）

目标：**先把数据记全**，不追求自动化。

- [ ] 定义 `params.yaml`（哪怕只有 5 个参数）
- [ ] 定义稳态判据（四个条件都写）
- [ ] 每次实验手工填 run record（先用 JSON 模板）
- [ ] 用表格/脚本做最简单的可视化

**验收**：能回答"上一次实验是什么参数、什么环境、结果多少"。

### P1：脚本化采集（2～3 周）

- [ ] 实验脚本自动产出 run record
- [ ] 原始数据进 Artifact，算 SHA-256
- [ ] 自动生成 DOE 点表（手工审核）
- [ ] 基础可视化看板

**验收**：不需要人工转录数据，跑完就有记录。

### P2：代理模型 + 推荐（3～4 周）

- [ ] 拟合代理模型（GP 起步）
- [ ] 报告 LOO 误差和适用范围
- [ ] 贝叶斯优化推荐下一个点（人审核后执行）
- [ ] 推荐附可证伪理由

**验收**：推荐的点比随机选点显著更好（用历史数据回测验证）。

### P3：自动闭环（谨慎，需人工 gate）

- [ ] 参数自动下发（仅限安全范围内的参数）
- [ ] 漂移自动告警分级
- [ ] 自动进入探索态（带先验）
- [ ] **人工 gate**：涉及物料成本、安全隐患的参数必须人确认

**验收**：连续运行一周无人工干预且指标稳定，同时告警准确率 > 90%。

> **P3 不是必须做的**。P0+P1 就能拿到 80% 的收益——数据记全了，后面所有分析才有可能。

## 10. 风险与边界（必须承认的做不到）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **代理模型外推失控** | 采样区外是幻觉 | 强制标记适用范围，超范围禁止推荐 |
| **过拟合当前批次** | 换了物料/环境就失效 | 必须跨批次验证，单一批次结果不认 |
| **稳态误判** | 观察窗口太短，刚好碰上一段好数据 | 窗口长度和 CPK 门槛不能为"快点过"而放宽 |
| **工艺全自动的安全风险** | 参数组合可能损坏设备或伤人 | 安全类参数一律人工 gate，不给 AI |
| **AI 编造物理原理** | 耦合解释听起来合理但错 | 耦合必须有实证，`verified: false` 的不能作为优化前提 |
| **实验次数被浪费** | DOE 设计不合理，点都打在无关维度 | 每批实验前必须回答"这批数据能/不能证明什么" |

**一条底线**：**这套系统的价值是让人的判断更准，不是替代人的判断。** 所有涉及成本、安全、不可逆的决策，人一票否决（原则 13 最小权限 + 原则 3 委托不委托判断）。

## 11. 与 23 条原则的映射

| 原则 | 在本系统中的体现 |
|---|---|
| 4 Spec 先行 | `params.yaml` + 稳态判据 = 研究的 Spec |
| 5 链路深究 | 耦合必须挖到原理，不能只记现象 |
| 8 并行思考 | 交 AI 前先有假设（认为哪个参数是主因） |
| 10 深度复盘 | 每轮实验后写"这轮学到了什么、下轮改什么" |
| 12 检测可观测 | 漂移监控 + 实验元数据完整 |
| 14 可回滚 | 参数锁定点要能一键恢复 |
| 17 人类策展 | 方法卡由人写，AI 只起草 |
| 18 证据保留 | 原始数据 + SHA-256，不只留聚合结果 |

| 22 持续质疑 | 每次推荐必须附可证伪理由 |

## 关键认知沉淀

> **工程类的瓶颈是验证带宽，工艺类的瓶颈是实验次数。** 前者靠并行和自动化，后者靠代理模型省实验。搞反了，钱和时间都会烧掉。
>
> **没有 `code_commit` + `config_hash` 的实验记录等于废数据。** 三个月后你无法判断两次差异是参数造成的，还是版本变了。
>
> **稳态判据必须同时有：指标 + 容差 + 观察窗口 + 退出条件。** 少一个，就等于没有定义——而"没有定义的稳态"会在验收时变成一场扯皮。
>
> **代理模型只在采样凸包内可信。** 跑到外面，它给的是带置信区间伪装的幻觉。
>
> **漂移后回探索态，但要带历史先验。** 不是推倒重来，是"我大概知道在哪，但需要重新确认"。
>
> 最后一条：这套系统让人判断更准，不替代人的判断。涉及成本、安全、不可逆的决策，人一票否决。
