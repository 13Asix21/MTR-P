## 第一篇：你的 Agent 需要一位经理

### 核心论点

> 让一个人成为优秀技术主管或经理的能力，直接转化为 AI 编程能力。一旦你开始并行跑多个 Agent，你就不再是调试上下文，而是在管理团队。

### 四种迁移技能

| 技能 | 具体做法 |
|---|---|
| **清晰的任务界定** | 写 brief 而不是写"感觉"。必含：结果、上下文、约束、非目标、验收标准、集成说明、验证方案 |
| **委派判断** | 分三档：完全委派（机械实现、样板重构）/ 委派但设检查点（涉及共享接口、易冲突）/ 不委派（架构、产品决策、安全设计） |
| **验证回路** | 要求 Agent 跑测试并附输出；要求 lint 和 typecheck 通过；要求结构化"PR 包"（改了什么、为什么、动了哪些文件、测试计划与结果、风险） |
| **异步检查** | 设检查节奏（"15 分钟没进展就停下来报阻塞"）；用固定格式问状态（改了什么？下一步？风险？需要我做什么？） |

### 两个硬骨头

1. **合并冲突会快速繁殖** —— 这不是工具问题，是边界问题。解法：一 Agent 一 PR、两个 Agent 可能碰同一文件就重新拆任务、共享接口由人主导的第一个 PR 先处理
2. **"该不该做"成为真正的瓶颈** —— 造东西变便宜了，你会开始造所有东西。AI 不消除对判断的需求，它抬高了判断的价值

### 两个管理概念

- **WIP 上限**：限制同时活跃的 Agent 流数量，否则会淹死在 review 里
- **Kill criteria**：在开始之前就定义"什么情况下放弃这个方向"

### 六步操作系统

```
像经理一样计划 → 像编排者一样派活 → 异步监控 → 激进验证 → 谨慎集成 → 复盘
```

## 第二篇：认知投降

### 核心区分

| | 认知卸载 | 认知投降 |
|---|---|---|
| 定义 | 把"怎么做"交出去，保留"做什么" | 完全停止构建答案，AI 的输出就是你的输出 |
| 类比 | 计算器、搜索引擎、GPS | 没有可比物——你没有形成独立观点可供比对 |
| 结果 | 你仍然能判断结果是否合理 | 没有可推翻的东西 |

### 关键数据（Wharton 研究，1,372 人）

- AI 错误时，**73% 的情况下参与者接受了错误答案**
- 更糟：有 AI 可用时**信心反而上升**，即使一半答案是故意错的
- 他们在借用模型的信心，当成自己的

### 软件工程为什么特别脆弱

1. **表面信号默认正确** —— 生成代码能编译、过 lint、能跑、长得像旁边的代码。表面正确 ≠ 系统正确，缝隙里藏的就是投降
2. **吞吐量是可见指标** —— PR 数、功能数、关闭的 ticket。这些都不区分"我建的我懂"和"Agent 建的我批准"
3. **信心会干净地转移** —— 模型用陈述句说话，代码评审把陈述句读成权威
4. **工作是复合的** —— 每次投降都让下一次更容易投降。投降是路径依赖的

### 五条校准启发

1. 读输出前先构建预期（哪怕猜得不好）
2. 像 AI 没写过一样读 diff（想象是一个初级工程师提交的）
3. 让模型反驳自己（第二遍成本极低，能打破借用信心效应）
4. 注意自己什么时候累（投降是疲劳现象）
5. 观察信心从哪来（如果你无法重建"为什么这么设计"，那是投降的产物）

### 抗投降的工程手段

- **验证作为硬性出口**：每个任务终止于具体证据，不是"看起来完成了"
- **反合理化表**：把常见借口和反驳预先写在一起
- **更小的范围、更小的 PR**："审查单元 = 理解单元"
- **学习时用概念查询而非生成**
- **设计摩擦**：生成前要设计文档、合并前要确认步骤
- **每周独处写代码**：不是道德练习，是校准练习

### 最后的框架

> 是"委托给"AI，还是"与之合作"？
> 委托产生投降；合作产生**相互放大**——你的 prompt 磨利模型输出，模型输出磨利你的下一个 prompt，最终磨利你对问题的理解。

## 第三篇：代码 Agent 管弦乐团

### 从指挥到编排

- **指挥模型**：一个 Agent，同步，上下文窗口是硬天花板
- **编排模型**：多个 Agent，各自上下文，异步，你在上面计划与检查

### 单 Agent 的三堵墙

上下文过载 / 没有专业化 / 没有协调。Subagent 解决前两个，Agent Team 解决三个。

### 三种模式

**Pattern 1 · Subagents（先从这里开始）**

父 Agent 用 Task 工具派生子 Agent，每个有明确 brief 和文件所有权。父 Agent 手动管理依赖图。缺点是：没有对等消息、没有共享任务列表、文件范围靠自觉。

**Pattern 2 · Agent Teams（真并行）**

三层结构：Team Lead / 共享任务列表 / Teammates。新增三个协调原语：任务状态与依赖追踪、对等消息、文件锁。

关键实践：
- 队友数 **3-5 是甜蜜区**，token 成本线性增长
- 高风险任务要求先写计划，Lead 审批
- **循环护栏**：`MAX_ITERATIONS=8` + 每次重试前强制反思（"什么失败了？什么具体改动能修复？我是否在重复同一做法？"）
- **专职 `@reviewer` 队友**：只读、只跑 lint/test/security-scan、每个任务完成时自动触发

**Pattern 3 · 规模化编排（三档工具）**

| 档 | 形态 | 代表 |
|---|---|---|
| Tier 1 | 进程内 subagent / team | Claude Code |
| Tier 2 | 本地编排器（worktree 隔离） | Conductor、Vibe Kanban |
| Tier 3 | 云端异步 Agent | Claude Code Web、Copilot Coding Agent、Jules、Codex Web |

### 三道质量门

1. **计划审批** —— 修坏计划比修坏代码便宜得多
2. **Hooks** —— `TaskCompleted` 时跑 lint 和测试，不通过就不让结束
3. **AGENTS.md 复合学习** —— 但是**必须人工策展**。研究显示 LLM 生成的 AGENTS.md 无益甚至有害（成功率降约 3%，推理成本增 20%+），人工写的约有 4% 提升

### 瓶颈已经转移

> 瓶颈不再是生成，是**验证**。

测试在改动前通过，不保证能抓住改动引入的回归；Agent 能写出技术上有效但漏掉关键 case 的测试；上下文窗口限制让大代码库上的 Agent 漏掉视野外的约束；**flaky 环境对单个开发者是烦人的边缘情况，对四十个 Agent 同时命中就是系统性阻塞**。

### 纪律

> 人类的瓶颈原本是特性，不是 bug。以人的速度，错误缓慢复合，痛感迫使早期纠正。带一支 Agent 军队，小错误复合的速度会超过你抓它们的能力。

### 两条不可让渡的

**委派任务，不委派判断**：
- 交给 Agent：有紧评估函数、能自测的工作；样板、迁移、测试脚手架、探索你手工没时间试的方案
- 留给自己：架构与 API 设计（Agent 在训练数据里见过大量烂架构，会很乐意把企业级模式 cargo-cult 进你的创业公司）；决定**不做什么**；带完整系统上下文的审查

**你的 spec 就是杠杆**：
- 编排五十个并行 Agent 时，模糊的思考不只是拖慢你，它会**增殖**
- 精确的 spec（清晰架构、集成边界、边界情况、不变量）会增殖成精确的实现
